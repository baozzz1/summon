# 操作规程(agent 自己执行)

这几件事有明确的触发时机,平时不占你的常驻上下文,**动手前读这一节**。
常驻约定里只留了各自的入口和最严重的禁令,细节在这里。

## 建定时器 / 提醒

用 `summon remind` 给**当前会话**建,到点 summon 把 `--content` 当作一轮新任务投给你:

```shell
summon remind --turn-id <本轮凭证> --when <节律> --content <内容> [--output progress|result] [--context resume|fresh]
```

- `--when` 取以下之一:`in 30m`、`at 2026-08-22T09:00`、`every 2h`、`daily 09:00`、
  `weekday 09:30`、`weekly mon,fri 10:00`、`cron 0 9 * * 1-5`。
  星期几认 mon..sun / Monday / 周一..周日 / 0..7。
- 用户说「明天早上九点」这类自然语言时**你自己换算**成上面的形态再调用,命令不做自然语言解析。
- `--output progress`(默认)展示执行过程与最终结果;`--output result` 静默执行、只推送终态结果
  (失败也会有一条明确结果)。周期日报、巡检这类只关心结论的任务优先用 `result`,显著减少群消息。
- `--context resume`(默认)续用该 chat 的现有会话;`--context fresh` 每次起跑前重置会话、从空上下文冷启
  (与 `/reset` 同一段拆除)。状态全在文件里的周期巡检用 `fresh`:跨天累积的会话历史对当轮没有信息增量,
  却让每轮都以冷缓存重写全部历史。到点时该 chat 正有一轮在跑、队列里已有别的消息、或有活跃子代理,
  该轮一律沿用现有上下文,不拆别人正在等的轮。
- 内容很长或有多行,用 `--content -` 从 stdin 读,避开引号转义。
- 定时器触发的那一轮里也能建,用来给自己排下一步。但同一会话连续 3 轮定时轮都没等到真人消息时,
  `summon remind` 会拒绝 —— 用户一直不回,自续就该停下。
- 建完会回一句「已建定时器 SCH-n:每天 09:00,输出:仅结果,下一次 …」,**把时间和输出模式跟用户核对**
  再算完事。
- 查看、停用、交接走 `summon schedules ls` / `rm <id>` / `mv <id> --agent <别名>`,这三条都不需要凭证;
  部分修改(含 `--context fresh|resume`)走 `summon schedules edit <id> …`。

**换执行者**用 `summon schedules mv <id> --agent <别名>`:群、节律、正文、id 全不动,只换由谁来跑。
id 不变这点很重要 —— 正文里若写着「完成后执行 `summon schedules rm SCH-12` 自停」,重建会让那句
指向错的 id,`mv` 不会。目标 agent 不在 registry 里会被当场拒掉:scheduler 查不到它的投递身份时
**跳过 tick 而不报错**,交接过去就成了不响也不报的哑弹。

⚠️ **绝不要手改 `~/.summon/schedules.yaml`**。那份表所有 agent 共用,写坏一个字段整份表都读不出来,
后果是**全部**定时器一起失效;手写还绕过了 id 分配的并发锁,两个 agent 同时写会互相覆盖。

## 结束当前会话

```shell
summon session end --turn-id <本轮凭证>
```

登记「本轮完成后退出」:本轮正常完成后会话退出,上下文保留,对方再发消息就接着这段上下文聊。
不发退出回执,本轮回复末尾会自动注明已退出。轮末还有排队消息或活跃子代理时不退;本轮失败、
被打断时这次登记作废。

## 读当前飞书会话的前文

当前模型上下文不保证包含这个会话的全部历史。

**什么时候读**:用户要求总结、复盘、分析可行性、梳理决策,提到「之前 / 大家 / 前文 / 前因后果」,
或当前消息里的指代和结论无法从已知上下文解释。问题本身自包含时不要为了保险机械拉历史。

**chat_id 只能这样取**:

```shell
CHAT=$(summon chat-id --turn-id <本轮凭证>)
```

⚠️ 不要读环境变量 `$SUMMON_CHAT_ID` —— 它是进程启动那一刻钉死的,会话被迁移后指向的是**上一个群**,
照它去读会读到别人的历史。也不按群名搜索、不猜、不改用其他 chat_id。

**读最近 50 条**:

```shell
LARKSUITE_CLI_NO_UPDATE_NOTIFIER=1 LARKSUITE_CLI_NO_SKILLS_NOTIFIER=1 \
  lark-cli im +chat-messages-list --as bot --chat-id "$CHAT" \
  --order desc --page-size 50 --no-reactions --format json
```

- 返回 `has_more=true` 且现有内容不足时,用返回的 `page_token` 继续同一查询
  (追加 `--page-token "<page_token>"`);也可用 `--start` / `--end` 缩小时间范围。
  读多少由任务所需决定,不要无边界拉取全部历史。
- 结果按 `desc` 返回,分析前**按消息时间还原对话顺序**,逐条区分发送人、正文和 `thread_id`;
  不要把不同发送人的话合并成同一人的观点。
- 相关消息带 `thread_id` 且回复会影响结论时,再按需读该话题:

  ```shell
  LARKSUITE_CLI_NO_UPDATE_NOTIFIER=1 LARKSUITE_CLI_NO_SKILLS_NOTIFIER=1 \
    lark-cli im +threads-messages-list --as bot --thread "<thread_id>" \
    --order desc --page-size 50 --no-reactions --format json
  ```

这是**只读**能力:不要为此执行 `auth login`、发消息或查询其他会话。若权限、API 或可见性失败,
或仍有 `has_more` 未读取,必须明确说明实际覆盖范围和缺口,绝不要把部分上下文说成完整全貌。

## 用户发来的附件

用户随消息发来的图片 / 文件 / 语音 / 视频,summon 会先下载到本地,并在消息末尾以
「(用户随这条消息发来 N 个附件…可用 Read 等工具查看)」给出本地路径。按需用 Read 等工具打开即可,
不需要额外命令。

## 跨群委派

`summon delegate` 向目标群发布公开摘要，把原始委派指令通过内部通道交给同一个 agent 在目标群执行。Owner 明确要求转群，
或本轮提示确认源群已开启自主分流授权时，可以使用。普通交办本身不代表跨群授权。

```sh
summon delegate --turn-id <本轮凭证> --to "已有群完整名称" --summary "可公开摘要" --content <私有正文|->
summon delegate --turn-id <本轮凭证> --new-chat "新任务群名称" --summary "可公开摘要" --content <私有正文|->
```

`--to` 与 `--new-chat` 二选一。`--to` 也接受 `summon chats` 的会话序号；服务端返回的候选 chat_id
可供 agent 内部消歧，**不要要求用户查找或填写群 ID**。群名按完整名称精确匹配，同名时让 Owner
根据群说明和成员范围选择，不能擅取第一项。找不到已有群时不能自行改为建群。

- 自主分流由 Owner 在主控群发送 `/delegate auto on` 开启，`/delegate auto off` 关闭，
  `/delegate auto` 查看。授权按源群保存并绑定 Owner 与 Bot 身份，后续真人任务轮会注明当前状态。
- 自主分流时，独立主题且需要持续跟进的任务优先复用合适群，没有合适群再新建。
  已有群须先核对成员范围，只在 `--summary` 中放该群可见的信息。
- 新群仅加入 Owner 与当前 Bot，Owner 为群主。建群由 daemon 执行并保存结果，投递失败后使用
  同一轮凭证和相同参数重试会复用已建群。结果不明时停止重试，交 Owner 核对。
- 可先加 `--dry-run` 检查目标与动作；预演不建群、不邀请、不发卡、不投递，也不占本轮名额。
- 正文最多 16000 字节，多行正文用 `--content -` 从 stdin 读取。正文写明目标、必要背景、约束、
  当前进展和验收条件；私有正文不出现在目标群卡片或预演输出中。
- `--summary` 最多 2000 字节，省略时使用固定提示，绝不以正文补摘要。摘要卡只含公开内容和随机详情标识，
  点击「查看委派详情」后服务端核验原委派人与当前 Owner、Bot 身份和卡片所在群，详情只私聊返回。
  普通对话或操作权限不能代替 Owner 身份。
- 只有 Owner 真人轮可用；定时轮、bot 发起的轮和委派来的轮均不可委派。每轮最多一项，
  相同任务重试只投一次。Bot 不在已有群时，通过与 Owner 身份一致的飞书 CLI 用户账号邀请。
- 目标群先收到摘要卡，agent 再通过内部任务队列收到完整指令；目标群忙时排队，重启后仍沿该群恢复。
  进度、报错、结果、追问及新建定时任务均沿目标群处理，源群回复说明目标群和投递状态。
- 该功能隐藏转发卡片中的原始指令，不隔离目标群的 agent 上下文，也不保证模型输出保密。
  正文只携带该群执行任务所需的内容，不要求 agent 在回复中复述原始指令。
- CLI 与 daemon 均须支持摘要与内部指令分离协议，版本不匹配时拒绝；不使用正文公开投递作为回退。

## 从源群 Fork 上下文

Owner 或有两端操作权限的用户在源群发 `/fork`，可通过卡片填写新群名或已有群完整名称；
也可发送 `/fork new 新群名称` 或 `/fork to 已有群完整名称`。新建群只向 Owner 开放。

已有群按完整名称精确匹配。同名时在卡片中选择，可先打开群核对；用户不用填写群 ID。
卡片仅发起人可提交，有效期十分钟，提交时重新核验源会话和两端权限。命令与卡片共用请求记录；
失败时通过原卡继续本次请求，不能通过反复发送新建命令处理结果不明的建群。

源会话保留，目标使用独立会话 ID，已有会话即使空闲也不能覆盖。准备完成后，到目标群发下一条
消息就会生成上下文副本；父历史不会作为消息刷入目标群。已签发的 `/fork #短码` 仍可在目标群兑换。
